# Mummy Maze Deluxe: behaviour notes of the game code

Working notes of the decompilation of `WinMM.exe` 1.1 (linked 2002-06-21, VC++ 6.0, image base 0x400000, plain exe with no
wrapper, RTTI for the 46 framework and library classes only). The game's own code is 0x401000 to 0x42d5b0 (424 functions
once `tools/gapfuncs.py` has found the virtual ones that Ghidra missed). Addresses are those of the 1.1 exe. No game text
is quoted here: texts are named by address (`GT(0x...)`).

## The framework

The 2002 SexyApp, older than Noah's Ark's (docs of `games/noahsark/docs/FRAMEWORK_2002.md` apply): `Widget` has 41 virtual
slots (Noah's 44), `SexyApp` 47 (Noah's 54), and `Dialog` 46. The widget slots the game overrides (by index; offset =
4 x index): 0 destructor, 1 AddedToManager, 2 RemovedFromManager, 12 Resize(x,y,w,h), 15 Draw, 16 Update, 22/23
MouseEnter/Leave, 24 MouseMove?, 25 MouseDown, 26 MouseUp. The widget manager keeps a key-down array, which the board reads.
The `SexyApp` slots the game overrides: 0 ButtonPress, 1 ButtonDepress, 2 ButtonDownTick (the ButtonListener part),
4 Shutdown, 10 LoadingThreadProc, 12 scalar-deleting destructor, 20 WriteToRegistry, 21 ReadFromRegistry, 24 (nothing),
26 Init, 39 NewDialog. Calls from the game through the app's vtable: 0x34 Popup, 0x38 SafeDeleteWidget, 0x60 Shutdown,
0x94 GetLoadingThreadProgress, 0x98 SwitchScreenMode(windowed), 0x9c NewDialog, 0xa0 DoDialog(id, modal, header, lines,
footer, mode), 0xa4 GetDialog(id), 0xa8 AddDialog(id, dialog), 0xac KillDialog(id).

## Files and tables

Images are `images\<name>` from the 165-entry table at 0x492410, sounds `sounds\<name>` from the 25-entry table at
0x4926a4 (ids in `src/Res.h`, generated by `tools/make_res.py`). Fonts: `data\font1.txt` (image FONT1), `headerfont`,
`biggestfont`, `scorefont`, `pyramidfont`. Music: `music\game.it`, loaded twice (slots 0 and 1) and played by order.

Application object fields (offset from the app; images array at +0x10380): 0x10380 images, 0x10384 font1, 0x10388 scorefont,
0x1038c headerfont, 0x10390 biggestfont, 0x10394 pyramidfont, 0x10398 title screen, 0x1039c main menu, 0x103a0 the
in-game buttons panel (0x412ea0), 0x103a4 level-complete screen (0x422480), 0x103a8 high-score screen (0x4143a0), 0x103ac
(0x414290), 0x103b0 world map (0x417010), 0x103b4 board (0x403e80), 0x103b8 victory screen (0x401ca0), 0x103bc side
panel (0x4291d0). 0x103d8 is the game mode: 0 classic, 1 adventure, 2 adventure finished, 3 classic finished, 4 tutorial
(5 to 8 are the tutorial's later parts?). The light mask, 256 x 256 bytes at app+0x380:
`mask[y][x] = clamp((int)(255 - 256 * (max(0, sqrt((x-128)^2 + (y-128)^2) - 80) / 48)^2), 0, 255)` (0x41dd60).

Registry values (`PopCap\MummyMaze`): LastScoreName, LastInternetScoreName, Speed (+0x10434, default 1), Name, Clock
(+0x1042c), Ankh (+0x1042d, default 1), and the tip flags TwoMummyNag (+0x10e8c), GateNag, TrapNag, RedNag, ScorpNag, DarkNag,
AnkhNag (+0x10e92), all default true.

Maze files: `data\mazes\B-<n>.dat`, 101 files of 1506 bytes (bit-packed walls, see Board::LoadMaze, 0x40e1d0).

## The board (0x403e80; Widget + ButtonListener at +0x4c; object 0xec8 bytes)

Fields (offset: meaning). 0x50 maze size (6, 8 or 10), 0x54 cell size in pixels (360 / size: 60, 45, 36), 0x58 app,
0x5c state, 0x60 the explorer, 0x64 and 0x68 the two mummies, 0x6c the scorpion, 0x70/0x74 a cached picture of the
board and its valid flag, 0x78/0x7c/0x80 the buttons (ids 0 and 2, "PLAY NOW", and the link id 3 shown after a level),
0x84 a 11 x 11 table of fade counters for the hover highlight (cleared 0x410ab0, aged 0x410a80, set by MouseMove 0x40e150),
0x26c start tick, 0x278 "can no longer be solved" flag, 0x27c/0x280 the mouse, 0x284/0x288 and 0x28c/0x290 the skull traps
(99 = none), 0x294/0x298 timers of the explorer's death scenes (-1 = off), 0x2a0/0x2a4 the gate cell (the gate is the barrier
below that cell), 0x2a8/0x2ac the key cell, 0x2b0 the maze number in its file (1 to 50), 0x2b4 the file number (data\mazes\B-<n>.dat),
0x2b8 the gate is closed, 0x2bc the gate's animation, 0x2c0 started, 0x2c1 a solution is being shown, 0x2d4/0x2e0/0x2ec/0x2f8 four
lists (0x2e0: the undo stack; 0x2ec and 0x2f8: the solver's visited states and its solution), 0x300 the cells: `int cell[x][y]` at
0x300 + (x * 10 + y) * 4 with the flags 1 wall to the north, 2 south, 4 east, 8 west, 0x10/0x20/0x40/0x80 the exit on the north,
south, east, west border; 0x490 four pairs of random dust positions (re-rolled every 10 updates), 0x4b0 red mummies
(vertical first) and the maze's "flip" nibble, 0x4b4 time base, 0x4b8/0x4bc a queued click (99, 99 = none), 0x4d0 and 0x4d8 two
fades, 0x4e0 dark pyramid, 0x4e4 the tutorial step, 0x4e8, 0x4ec, 0x500 a random generator (MTRand), 0xec0/0xec1 flags.

States (0x5c): 0 the explorer walks in, 1 waiting for a move, 2 the explorer moves, 3 the scorpion moves, 4 and 5 the first and
second mummy step, 6 the explorer reaches the exit, 7 after the scorpion, 8 the explorer is caught, 9 lost (the game-over panel),
10 level complete, 11 the solver runs ("Solving Puzzle", started by the ABANDON HOPE button), 12 and 13 the ending scenes.

Maze file (0x40e1d0): the file holds a series of mazes of one size; the loader reads `mazeNumber` of them in order and keeps the last.
First byte: low nibble the size, high nibble the red/flip flag; then five bytes (the second unused): mummy count, gate present, skull
traps, scorpions. Per maze: the walls (two passes of `size` rows, one bit per cell, a second byte for cells 8 and up), the exit
border byte, the explorer's entrance, the mummies', the scorpion's, the traps', then the gate and key cells. When the flag is set the
coordinates are mirrored (`size - 1 - y`). The explorer starts outside the maze, next to the border cell of the entrance byte, and
walks in (state 0).

The entities are Widgets that the board draws: 0x426e70 the explorer (Update 0x426f70: idle animation), 0x421b40 a mummy (id in +0x74;
Update 0x421bf0 blinks), 0x429120 the scorpion. Sound pan of a column x: `(int)((half - px(x)) / (2 * sum) * 800.0)`, sum = cell * (size + 1),
half = sum / 2, px(x) = cell * x + 0x36 (py(y) = cell * y + 0x50).

## The adventure (world map 0x417010, saved games, slot dialogs)

The map is a Widget (object 0x22c bytes; ButtonListener at +0x4c) with the app at +0x50, the pyramid the marker stands on
(+0xb4), the one it walks to (+0xb8) and the next one on the way (+0xbc), then fifteen ints at +0xc0, one for each pyramid: -1 shut, 0 to 14
chambers done, 15 solved. Widgets: +0x64 ENTER (id 99), +0x68 the save-and-quit corner (id 98), +0x6c, +0x70, +0x74 the three
corners that open the statistics, the player's name and the treasure chest (ids 50, 51, 52), +0x78 the fifteen pyramids
(class 0x427050, ids 1 to 15). The marker (+0x100, +0x104) walks one pixel per update on each axis along the six waypoints of a
path (`kMapWay`, path numbers 1 to 19, `kMapEdge` says which path joins two pyramids and, by its sign, whether it is walked
backwards), with `kMapLinks` the graph and `kMapPos` the pyramids' places; the next pyramid on the way is the neighbour nearest to the target by a
recursive count (0x418a30, 0x4189b0). A solved pyramid opens its neighbours (0x419940, the table is in the code: pyramid 0 opens 1 and
6, 1 opens 2, 2 opens 1 and 3, and so on), and the last pyramid (14, the tomb) opens when the first fourteen are solved.

Flow: the main menu's Adventure link sets the game mode to 1 and calls 0x41b800: with saved games it shows the slot dialog (id 10,
five slots, a DELETE GAME button, Cancel), else the dialog for a new name (id 11). A slot loads through 0x41bcc0: no file means the name
dialog; a file is read by the map's constructor (bad format: the main menu comes back with a message). A chamber that is won sets
app+0x10408; the next map (made by LoadAdventure(slot, true)) counts it, saves, and goes straight on into the pyramid's next chamber,
or, when the pyramid is solved, shows its treasure (game mode 2, the ending board) whose link leads back to the map. Being caught
makes a map from the saved file (so the time and the catches are those of the file), adds one catch and saves (0x41c300 saves
whenever it removes the map). When the last pyramid is solved the victory screen comes and the saved progress starts again from zero.

Saved game (`data/saves/adv<n>.sav` in the original, `adv<n>.sav` in the user folder here): int length and the player's name, int 2 (the
format), int length (0x9c0) and the app's random generator (app+0x104cc: its 624 state words, 0x4195d0 writes them with 0x432760, 0x417010
reads them with 0x4326d0), int length and the progress as a Buffer's web string (the 15 values as bytes, 0xff for a shut
pyramid), a byte for the pyramid the marker stands on, a double for the seconds played (app+0x10418), an int for the catches (app+0x10420).

The map's marker byte sets the current pyramid only when it is below 0x10 and the target pyramid always. The ENTER button's picture is a
0x118 x 0x2d crop of the buttons' sheet, at y 0 for a pyramid with no chamber done and y 0x2d after that; it is cropped again each time the
marker arrives. After the solved-pyramid branch of the map's Update (0x417c10) the original goes on with the hover, the marker and the twinkles.

The classic game's saved file (`data/saves/classic.sav`, 0x410b70 writes it, 0x41c600 reads it): int 2, an int 0x9c0 and the board's random
generator (board+0x500), an int length and the app's Buffer (+0x103ec: the data for the Internet score list, as a web string; the main
menu's classic link clears it and writes a byte, the registered name and code and the time, the level-complete screen adds a 0 byte and the
level's seconds, Abandon Hope a 1 byte and the score), then the chamber, the pyramid, the maze, the file, the score, a byte for a level
that was done, the time played in updates and the game mode. A level that was done is not played again: the loader moves on to the next
chamber (and pyramid), takes the file as (pyramid x 99 + chamber x 7) / 15 (at most 99) and draws the maze number as
abs(rand() % 7) + chamber x 99 / 15 + 1, a second time when the first number is 100 or less (it always is), until the pair is not in the
table at 0x492708 (483 pairs). The high scores file is written by the destructors of the high-score and victory screens, not when a name is
set; a record whose check fails keeps its name and its score becomes the stored one modulo 256.

The original's search for a way out (the one behind the Ankh and ABANDON HOPE, 0x405580 and 0x411a90) does not know that a mummy that
wins a fight with the other one flips the gate when it is on the key stone (0x407cc0 calls 0x421d00 when the fight ends); the board does,
so a solution can be one turn wrong. The test bot searches again from where the explorer stands (`Board::FindWay`).

## The standard test commands (`src/testhooks/TestCommands.cpp`)

The commands of `docs/TEST_COMMANDS.md`, reached only from a test (`-script`, `-commands`, the web test page's `command`). A
command that is never given changes nothing and draws no random number. Each answers `STATE {...}`, `MOVE {...}`, `OK <command>` or
`ERROR <command>: <reason>`.

| Command | Does |
|---|---|
| `state` | one JSON line. Always: `screen` (loading, title, menu, map, board, complete, lost, highscores, victory, dialog), `mode` (classic, adventure, tutorial, classic-treasure, adventure-treasure), `pyramid`, `chamber`, `level` (pyramid x 15 + chamber + 1), `score`, `update`, `over`, `botmode`, `stepinput`; with a dialog up `dialog` (its id); in the adventure `deaths` and `seconds`; on the level-complete screen `levelSeconds`; with a board `moves` (the undo list), `timer` (the clock on the board) and `board` (`size`, `state`, `ready`, `maze`, `file`, `dark`, `red`, `gate`, `key`, `unsolvable`, `explorer`, `mummy0`, `mummy1`, `scorpion` as `[x, y, alive]`) |
| `goto <screen>` | from the title: `menu` (presses the play link). From the main menu: `classic`, `adventure`, `tutorial`, `options`, `highscores`, `credits`, each through the menu's own link or the dialog's own function |
| `level <n>` | a classic game from chamber n (1 to 225) from the main menu, as `-autoplaystart` does it; on a classic board it restarts the board at that chamber |
| `unlock all` | opens every pyramid on the adventure's map (nothing else in the game is locked) |
| `set score <n>`, `set botmode classic\|adventure\|tutorial`, `set stepinput keys\|clicks` | the score; what `move` starts from the main menu; whether a step of the explorer is the arrow key or a click on the cell |
| `win`, `lose` | `OnLevelComplete` (the explorer has left the maze), or `Board::Lose` (the game-over panel; `AdventureCaught` in the adventure) |
| `seed <n>` | seeds the C library generator, the one every draw of the game comes from |
| `move` | the bot's next move as `MOVE {"kind", "input": [...], "updates": n}`, where `input` is the real input in order, `{"click": {"x", "y"}}` or `{"key": "<DOM name>"}`, in game coordinates; `MOVE null` when there is none |

`move` plays whatever screen the game is on: the title's play link, the menu link of `botmode`, the slot dialog's first slot, the
name boxes (a click, `bot`, the Yes button), the world map's first open pyramid, the level-complete link, the lost panel's try-again
link and the tutorial's buttons and its allowed move. On a board it follows the solver's way out (`Board::FindWay`, the search of
Abandon Hope, from where the explorer stands): the plan is made once and followed while the board keeps to it, and made again when
it does not (a new search at every step walked in circles, because the depth first search that keeps the shortest way it found does
not always give the same first step). When there is no way out it presses RESET MAZE. It has no dice, unlike the autoplay bot of
`Autoplay.cpp` (which takes random walks and undoes on purpose): it always wins the chamber, so a whole game ends at the victory
screen. `over` is true on the victory screen and on the high score table after a lost game once the name is asked, and, with
`botmode tutorial`, once the tutorial has handed over to the classic game.

A key is held for one update to take one step (`Board::UpdateExplorer` reads the key table at the next update); in a `-fast` run a
driver whose answer takes longer than a step holds the key through the next step too, so long `-fast` runs use `stepinput clicks`
(`Board::MouseDown`, the cell next to the explorer, which takes a step at once) and the arrow keys are played in real time.

## Fix candidates

What the original does that the fixes mod (`mods/fixes`, below) mends, and what it left alone.

- **Made: the clock of a chamber.** The original times a chamber and the adventure's total by `GetTickCount` (the bonus of a classic
  chamber, `LevelCompleteScreen`, 0x422480; the time kept by `Adventure.cpp`), while the clock on the board counts updates. A slow
  moment or a long pause costs bonus points, and two runs of the same input do not score alike. `gameClock` counts the updates
  (`MummyApp::GameTick`), as the bot's and `-fast` runs already do. In a play with no pause and no slow machine the seconds are the
  same.
- **Made: the key-stone fight in the search.** When mummy 1 meets mummy 0 the board lets mummy 0 win, and when the fight ends
  `Mummy::OnArrived` (0x421d00) flips the gate if the winner stands on the key stone, whether it moved this turn or not and whether
  the key was used earlier in the turn. The search of the Ankh and of Abandon Hope (`SolveRec`) flips it only for a winner that moved
  and the key not used yet. `solverFight` flips it in the other cases too. No bot game of the suite (1200 chambers) meets the case, so
  it is checked against the board's code and not by a played game.
- **Not a fix: the Ankh works only on the 6 x 6 mazes** (`CheckSolvable` returns for size 7 and over). It is a design limit of 2002
  (the search is too slow on the larger mazes there), and turning it on for the others gives the player information the game never
  gave: a mod, not a fix (`MOD_IDEAS.md`).
- **Not a fix: the two debug files** (`debug.txt` at every maze load, `badmaps.dat` when the search finds nothing) are not written
  by the port.

## The fixes mod (`mods/fixes`)

`mod.json` with the feature `fixes` and one bool setting for each fix, `gameClock` and `solverFight`, both on by default and applied
at a restart (the game reads them once, in `Init`: a chamber never changes its clock halfway). `src/ModFixes.cpp` reads them; without
the mod every fix is off and the game is the original. The site ships it beside the page and starts the game with it on
(`cmake/ByopopWeb.cmake`); natively it is a folder in `mods-mummymaze`, or in a `-modsdir`. It does not split the high scores
(a feature, no rules or tunables): the scoring is the same and only the clock is another.

## The drivers that play by `move`

`tools/realplay/drive.py` plays a game natively: it starts the exe under rundesk with `-commands` and `-realinput`, asks `move` for
each step and sends it as real SDL events (`click game X Y`, `keydown` and `keyup`), and reads `state` to know when a step is taken
and when the game is over (`--mode classic|adventure|tutorial`, `--stepinput keys|clicks`, `--fast`, `--steps`, `--at N:<lines>` for
focus, full screen and resize in the middle of a game, `--finish`). On the web the test page's `byopop.test.playByMove` plays by the same
`move` as DOM events. A `move`'s `input` is the ordered list of `docs/TEST_COMMANDS.md` (`{"click":[x,y]}`, `{"key":"ArrowUp"}`).
Both stop with a message when the bot has nothing to press, when a chamber takes more than 500 moves (a loop) or when the screen
does not change (`--maxmoves`, `--stuck`). A native run in `-fast` reads the game's clock in updates and the driver is slower than
the game, so the game runs on while the driver thinks: the clock of such a run (the level-complete bonus, the adventure's seconds)
is not a player's, and its scores are lower than the same moves played in the page, where `hold=1` stops the game between the
driver's calls.

## Registration and the buttons that lead out of the game (taken out 2026-11-08)

The port was the registered game already (the shareware branches were never translated); what was still in it is gone now, and each
removal leaves the baseline's logs and screenshots alone except where it is said.

- The Options dialog's Register button (id 1, which showed the register message) and the button that opened the game's web page
  (id 3, "Visit PopCap.com"). The Tutorial and High Scores buttons now share the first row and Credits takes the second, so the dialog
  keeps its size and has no gap. This is the one visible change; the suite's three Options photographs changed with it and the
  baseline was refrozen at that commit.
- The title's register link (never shown in the registered game), the play counters behind it (`mDivisor`, `mPlaysShown`,
  `mDelayed`, `mDelayProgress`, `mClicked`), the title link that quits when the demo is used up (`mQuitLink`, never set), the
  register dialog's id, and the three `TimesPlayed` increments (a game started, a classic game continued, a slot played). The
  framework's `TimesPlayed` registry value is no longer written by the game. Not touched: the framework's own `mIsRegistered` (always
  true), which is the coordinator's to take out of `SexyApp`.
- The pictures `register` and `registerrunes`, which only the registration screen used (`make_res.py` leaves them out, so the image
  ids after them moved up by two; `NUM_IMAGES` is 163).
- Kept because the registered game has them: the `trialcircle` picture on the title, the "Internet scores" data buffer the classic
  link starts, the tips.

Loading was already as fast as the machine allows: the loading thread runs in one go after the first frame (the framework), it loads
the 25 sounds and the fonts without waiting, and the title polls its progress every fourth update. There is no minimum time.
